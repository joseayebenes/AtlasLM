VS Code para Ada con atlas

Cómo dejar VS Code listo para programar en Ada con el agente de Copilot, el modelo del gateway corporativo (gemma-4) en lugar de los de GitHub, y atlas como servidor MCP para que el agente conozca requisitos, documentos y trazabilidad.

Qué hace cada pieza

Modelo

gemma-4 del gateway

Se añade como Custom Endpoint (BYOM). El agente de Copilot lo usa en modo agente, sin modelos de GitHub.

Lenguaje

Ada & SPARK de AdaCore

Navegación, errores, compilación y depuración, sobre GNAT y gprbuild instalados con Alire.

Conocimiento

atlas por MCP

Cinco herramientas que solo leen: build_context, search, trace, impact y find_symbol.

Agentes

atlas y ada

AGENTS.md explica el proyecto; el agente atlas responde preguntas y el agente ada programa y le pregunta antes de cambiar nada.

Esta configuración traduce a VS Code la que se midió en OpenCode el 28 de octubre (94 % de acierto con la mitad de tokens). VS Code no se pudo medir del mismo modo, y lo marcado como por comprobar sale de su documentación, no de una prueba.

1Instalar

  1. VS Code y la extensión GitHub Copilot Chat, que es la que tiene el modo agente, también con un modelo propio.
  2. La extensión Ada & SPARK for Visual Studio Code (AdaCore.ada). No trae compilador.
  3. GNAT y gprbuild con Alire, en una terminal:
PowerShell
alr -n toolchain --select gnat_native gprbuild
  1. atlas, desde el repositorio (el perfil de 5 herramientas está en develop, aún sin versión publicada):
PowerShell, en la carpeta de AtlasLM
python -m venv C:/atlas/venv
C:/atlas/venv/Scripts/python -m pip install -e ".[all]" -c constraints.txt

2El modelo del gateway

En VS Code: paleta de órdenes → Chat: Manage Language Models → Add Models → Custom Endpoint. Pon un nombre de grupo, la clave y el tipo Chat Completions. VS Code abre chatLanguageModels.json; déjalo así:

chatLanguageModels.json
[
  {
    "name": "Gateway",
    "vendor": "customendpoint",
    "apiKey": "${input:gatewayKey}",
    "apiType": "chat-completions",
    "models": [
      {
        "id": "gemma-4",
        "name": "gemma-4 (gateway)",
        "url": "https://gateway.empresa/v1/chat/completions",
        "toolCalling": true,
        "vision": false,
        "maxInputTokens": 180000,
        "maxOutputTokens": 8192,
        "thinking": true,
        "modelOptions": { "reasoning_effort": "low", "temperature": 1.0 }
      }
    ]
  }
]
  • toolCalling: true es obligatorio: sin él el modelo no aparece en modo agente.
  • maxInputTokens + maxOutputTokens no pueden pasar del contexto del modelo (unos 200 000 tokens en el gateway).
  • reasoning_effort: "low" es lo que mejor funcionó en las pruebas: sin razonamiento gemma no sigue las cadenas de varios saltos. Por comprobar que el gateway lo recibe así desde modelOptions.
  • Si el gateway pide una cabecera propia para la clave, va en requestHeaders del modelo.
  • Después elige gemma-4 (gateway) en el selector de modelos del chat. Si no aparece, reinicia VS Code.

Sin cuenta de GitHub

Un modelo propio funciona sin cuenta de GitHub ni plan de Copilot en las sesiones Local del chat. En ese caso, los títulos y mensajes de commit también tienen que ir al modelo propio. Según la documentación de octubre de 2026 (por comprobar en el puesto), estos ajustes de usuario lo dejan así:

settings.json de usuario
{
  "chat.editor.localAgent.enabled": true,
  "chat.defaultToCopilotHarness": false,
  "chat.editor.preferCopilotHarness": false,
  "chat.byokUtilityModelDefault": "Main Agent Model"
}
Copilot Business o Enterprise. El administrador tiene que permitir la política Bring Your Own Language Model Key in VS Code; si está apagada, el modelo propio no aparece.

3La red corporativa

VS Code usa el almacén de certificados de Windows, donde ya está la raíz corporativa que inspecciona TLS. El proxy se le da en sus ajustes:

settings.json de usuario
{
  "http.proxy": "http://proxy.empresa:8080",
  "http.proxyStrictSSL": true,
  "http.systemCertificates": true
}
  • La documentación del modelo propio no dice si sus peticiones pasan por http.proxy (por comprobar). Si el gateway es interno y va directo, no hace falta proxy para él.
  • El servidor de atlas no hereda nada de esto: arranca con su propio entorno. El proxy y la clave se le dan en un fichero fuera del repositorio (paso 5).
  • El gateway admite 28 peticiones por minuto. Un agente que encadena llamadas rápidas puede recibir un 409 o un 429; si pasa, la respuesta tarda más o se corta.

4El proyecto Ada

La extensión necesita saber qué proyecto GPR abrir. En la carpeta del proyecto:

.vscode/settings.json
{
  "ada.projectFile": "tms.gpr",
  "ada.scenarioVariables": { "BUILD_MODE": "debug" },
  "chat.useAgentsMdFile": true
}
  • Cambia tms.gpr por tu proyecto, y quita ada.scenarioVariables si el GPR no tiene variables de escenario.
  • GNAT tiene que estar en el PATH con el que arranca VS Code. Lo más sencillo es abrirlo desde Alire: alr exec -- code . en la carpeta del proyecto, o añadir la carpeta bin de la toolchain de Alire al PATH de la cuenta.
  • Compilar: paleta → Ada: Build current project. Ejecutar: Ada: Build and run project main.... Depurar: configuración de tipo ada en launch.json.

5atlas como servidor MCP

Junto al GPR, un atlas.toml con el código, DOORS y los documentos, y el modelo del gateway para procesar:

atlas.toml (lo que importa aquí)
[llm]
base_url = "https://gateway.empresa/v1"
model = "gemma-4"
api_key = "${ATLAS_API_KEY}"

[sources.code]
roots = ["src", "tests"]
languages = ["ada"]
req_tag = "Req:"
test_patterns = ["**/tests/**"]
# solo si añades hephesto (paso 7): la carpeta bin de GNAT que dejó Alire
# tool_path = ["C:/ruta/de/alire/toolchains/gnat_native_*/bin"]

[mcp]
profile = "editor"      # las 5 herramientas; es el de por defecto con código

Después, con el Python de atlas, una vez:

PowerShell, en la carpeta del proyecto
C:/atlas/venv/Scripts/python -m atlas init --vscode
C:/atlas/venv/Scripts/atlas doctor atlas.toml
C:/atlas/venv/Scripts/atlas run atlas.toml

atlas init --vscode escribe .vscode/mcp.json. Añádele envFile, para que el proxy y la clave no queden en el repositorio:

.vscode/mcp.json
{
  "servers": {
    "atlas": {
      "type": "stdio",
      "command": "C:/atlas/venv/Scripts/python.exe",
      "args": ["-m", "atlas", "serve", "atlas.toml"],
      "cwd": "${workspaceFolder}",
      "envFile": "${userHome}/.atlas/atlas.env"
    }
  }
}
%USERPROFILE%/.atlas/atlas.env (fuera del repositorio)
ATLAS_API_KEY=...
HTTPS_PROXY=http://usuario:contraseña@proxy.empresa:8080
NO_PROXY=gateway.empresa

Comprueba que arranca: paleta → MCP: List Servers → atlas → Start Server, y en la salida MCP: atlas debe aparecer with 5 tools (profile editor).

6Los agentes

Tres ficheros en el repositorio del proyecto. AGENTS.md es lo que más cambió el acierto en las pruebas: sin él, el agente confunde el parent de DOORS con el requisito que se satisface. Cambia los nombres de módulos, documentos y unidades por los de tu proyecto.

AGENTS.md
# The project

An engineering project: requirements in DOORS, specifications and manuals, and Ada code. The atlas
MCP server knows all of it and how it is linked: ask it before reading files, and answer questions
about requirements, documents and traceability from what it returns.

## The project and its tools

DOORS: `SSS_MISSION` (system requirements) <- satisfied by `SRS_TMS` (software requirements of the
track function; some refine another SRS) <- verified by `STP_TMS` (test procedures). Documents: the
specification PDFs (they restate the SRS) and `hmi_manual.md`. Ada code: units `tracks` and
`logger`, tests in `tests/`; the code cites its requirements with `-- Req: <ID>`.

- Requirement ID -> `trace`. What it satisfies: `ancestors`/`links_out` (never `parent`, which is
  only its place in the DOORS outline). Who satisfies or refines it: `links_in`.
- Code name or `file:line` -> `build_context` (`find_symbol` if unsure); a change -> `impact`.
- Text or values of the documents -> `search` (narrow with `document`, `module`).
- Chains: one tool per hop, with the IDs the previous one returned. An error with `similar`: retry
  with the suggestion.
- DOORS and a document disagree (`values_differ`): give both, DOORS is the reference. Empty
  `implemented_by`: no code yet, say so.

Write IDs and names as the tools do and cite the source of each fact.
.github/agents/atlas.agent.md
---
name: atlas
description: Knows the project's requirements (DOORS), documents, Ada code and their traceability; use it for any question about them or about what a change affects
target: vscode
tools: ['read', 'search', 'atlas/*']
---
You answer questions about an engineering project (standards and specifications, requirements in
DOORS, Ada code) with the tools of atlas, the MCP server that knows the project. Answer from what
the tools return, never from memory, and cite the requirement IDs, code identifiers and documents
you rely on. Answer briefly. You never change files: when asked for a change, say what it affects
and which requirements and tests are involved.
.github/agents/ada.agent.md
---
name: ada
description: Changes the Ada code of the project; asks the atlas agent about requirements and traceability before changing anything
target: vscode
tools: ['read', 'search', 'edit', 'execute', 'agent']
agents: ['atlas']
---
You change the Ada code of an engineering project (requirements in DOORS, specifications, Ada).
Before changing any code, run the subagent `atlas` with the question you need answered (which
requirements the code implements, what a change affects, what a requirement asks) and use its
answer, with its IDs and sources.

Make one small change at a time. After each change, build in the terminal with
`gprbuild -P tms.gpr -q` and fix every error before going on; then run the tests that atlas
named. Cite the requirement a subprogram or type implements in a comment `-- Req: <ID>` next to
its declaration. Do not change code you were not asked to change.
  • atlas para preguntar: solo lee y gasta la mitad de tokens que el agente general.
  • ada para programar: no tiene las herramientas de atlas, se las pide al subagente atlas (agents: ['atlas']), así sus resultados no llenan el contexto del que programa.
  • El modelo de cada agente se elige en el selector del chat; no hace falta ponerlo en el fichero.

7Opcional: que el agente compile y juzgue con hephesto

atlas solo lee. Si quieres que el agente compile un fichero, pase las pruebas y reciba el juicio de cada cambio como en hephesto develop (qué compila, qué pruebas avanzan o retroceden), añade el servidor de hephesto:

PowerShell, en la carpeta de AtlasLM y luego en la del proyecto
C:/atlas/venv/Scripts/python -m pip install -e "./hephestolm[all]" -c constraints.txt
C:/atlas/venv/Scripts/python -m hephesto init --vscode

Ofrece check_code, run_test, run_tests y judge_changes. Añade 'hephesto/*' a las tools del agente ada.
